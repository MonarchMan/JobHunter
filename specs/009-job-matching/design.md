# 009 职位匹配与建议设计

新增 objective-v5 规则身份，复用 v4 的明确条件解析，新增岗位方向软评分条件，按岗位/地点/其他条件分组展示，每条适用条件等权。目标细分不匹配不给方向分，未提供分类或无法归类时标未知；其他硬过滤保持原判定。模型采用独立 v4 Prompt/Agent 身份，明确综合评价所有维度；完整偏好与学历等脱敏输入参与缓存身份，缺失字段不能推断满足。事实输出仍仅引用职位原文字段，不将个人评价存成职位事实。

JobAdvice v3 删除引用目录和还原逻辑，历史建议及 job-advice 运行输出通过迁移删除引用和简历重点、更新哈希。文本结构合法不能代替事实校验，事实评测使用人工黄金标注。

> 状态：Implemented

## 规则与模型两阶段加权评分

评分任务分为规则评分与模型评分两个阶段，最终总分按规则 30%、模型 70% 加权求和并限制在 0..100。规则阶段沿用既有 v1/v2/v3 证据引擎产出 `rulesTotal`；模型阶段由职位理解 Agent（JobUnderstanding 2.0.0）在同一次运行中额外输出 0..100 整数 `fitScore` 及 1-5 条中文理由。`composeMatchScore(rulesTotal, modelScore)` 是纯函数：`modelScore` 为空时降级为规则分并标记 `scoringVersion = rules-v1`，否则加权并标记 `weighted-v1`。加权后的模型贡献作为独立 `dimension: 'model'` 分项追加到 components，上限 70，携带模型分与理由证据，规则分项与既有引擎不变。

降级路径：模型未配置（端口注入 `unavailable`）或理解阶段在最后一次尝试（`context.attempt >= 3`）仍失败时，理解 Handler 返回 `fitScore: null`，匹配阶段以规则分完成，任务成功而非失败；建议阶段是否运行由独立的求职建议开关决定，不受模型降级影响。

`modelScore` 与 `scoringVersion` 持久化到 `match_results`（迁移 0046，历史行 `scoring_version` 默认 `rules-v1`、`model_score` 为 NULL）。模型分是非确定性输出，**不参与** `buildMatchIdentity` 的身份哈希，只有 `scoringVersion` 参与，避免同一有效输入因模型抖动产生重复记录。理解 Agent 输入新增画像快照（目标角色、领域、年限、技能），但其持久化的职位理解事实仍只按职位存储且不含画像内容（Prompt 规则 6）；`fitScore` 只随该次匹配调用传递，不写入 enrichment。

## 历史 v4 条件判断与语义评分分工

建议 Agent v4 删除 uncertainties 输出字段，需要确认的条件归入 preparation，模型最多输出五项准备行动。历史 v3 建议在读取时将待确认文字合并去重到准备建议（最多八项），不改写历史数据和哈希；Web 与 CLI 都只显示亮点、缺口、准备建议。规则资格的 unknown 状态仍独立保留。

批量入口全量校验后提交 match.score-batch，复用单职位处理器但不另行入队。TaskHandlerContext 提供受当前租约和尝试次数约束的 checkpoint，逐项保存到任务 result。retryPayload 将已保存结果并入批次输入，成功项直接跳过，失败项通过单职位 retryPayload 恢复阶段。批次失败汇总为一个可重试错误，不吞掉单项失败。

Agent 相同执行输入重试通过仓储原子恢复失败记录，保留 ID 和累计用量，清空旧错误及输出。任务上下文作为执行作用域，批次内不同职位由输入哈希区分；工具调用序号持续递增，保留历史调用。敏感 Agent 禁用缓存仍可通过显式任务作用域恢复失败记录，成功输出不复用。

新建 objective-v4 引擎，复用 v3.2 资格解析而不调用技能、项目、工作经历关键词评分。去掉未设置的偏好、招聘类别路由及豁免/优先条件，剩余条件等权计算已确认满足比例；未知保留 unknown 和完整度，只有 fail 排除。规则结果汇总为 qualification 分项，原始条件结果仍可查看。默认规则使用新 ID，旧规则定义与历史结果保持不变。

职位理解 Agent v3 输入补齐项目、工作经历、作品、竞赛、语言等语义材料（不含联系方式），按实习/校招/社招区别评估能力和职责相关性，缺失证据不得直接等同于没有能力。事实抽取仍只引用职位字段，fitScore 不写入职位事实。提示词与输入共同参与缓存隔离。总分沿用 30/70；仅规则模式及模型失败只代表条件匹配，不宣称完成能力评分。

## v3.2 毕业资格修复

新增纯函数毕业条件消费者，仅在新版本校招/实习资格路径使用。识别届别列表、范围及明确毕业年月窗口，保留原文和画像教育日期证据；年月按月份闭区间比较，不读取当前时间、不推断在读身份或学位授予。多个可能适用日期使用一致性判定，缺失或混合结论为 unknown；“均可”等非封闭列举不用于排除。窗口解释同句届别，不重复套用公历年份。剥离已识别片段后继续检查同句学历、在读等剩余条件；无法解释的括号/逻辑不擅自拆解。v3.2 独立版本及 ID，v3/v3.1 路径保持不变。补合成正负边界与版本集成测试，再复跑同一冻结 AI 开发参考集，不修改真实运行库。

## v3.1 介绍过滤边界修复

介绍过滤只在空行后的编号段落以明确职责动作或任职资格信号开头时恢复；仅空行、技术栈介绍、福利清单不触发。显式职责/要求标题始终恢复。v3.1 使用独立引擎标识与规则 ID，传递边界策略到资格、技能、实践三个消费者；v3 不启用新策略，保留旧结果重放。改动不扩展届别或技能政策。通过合成边界测试及同一冻结真实开发集复跑验证，不修改真实运行库。

## v2 类型化规则

### 后续 v3 条件与证据引擎

v3 为独立版本，保留 v2 模块与定义；默认入口改用新 ID，不修改既有规则哈希。新增纯函数条件语言、技能证据与实践匹配模块，共用三类顶层权重及既有分项/规则结果契约，不修改 UI 或数据库表。规则模式不调用 LLM；语义增强中的技能仍需按引用原文还原否定和任选关系，不能覆盖原文明示的豁免。

先将资格语句解析为 all/any/atom 节点，原子包含字段路径和 required/preferred/waived 模式；保守处理局部修饰、数值比较与缺失。unknown 在 all/any 中按三值逻辑聚合。资格歧义不得被 skill 命中掩盖。短句数值规则支持阿拉伯和常用中文数字；原文与比较值分开保留。

技能按要求组计算覆盖：必需/优先权重 3:1，any 组取最佳一项，独立要求分别计分。否定与计划内容不作为正证据；技能栏明确自述能力最高提供 0.8 覆盖，工作/项目中的实际使用证据提供 1.0。同一技能不累加不同来源。实践取最佳一条，技能相关性占 50%、职责对象覆盖占 30%、与命中职责关联的参与/负责/交付证据占 20%；参与 0.4、明确负责 0.7、负责且有交付或验证证据 1.0，均要求职责对象匹配。没有可识别的职位职责时不假造贡献，缺失信号保留其份额并说明。此为可解释初始政策，不宣称真实排序准确率提升。

“经验不限”不再将经历设为不适用；v3 仅类别配置中的零权重维度为不适用。v2 的“不限即重分配”仅保留用于历史重放。第 5 项人工样本评测不在本次范围内；本次只增加确定性边界、来源证据、不变性与版本集成回归。

统一引擎按不可变 JobRevision.recruitmentCategory 选择三套权重；旧快照可从标题/用工类型中明确的实习、校招、社招文字回退，歧义保持 unknown，禁止读取全局同步设置。v1 算法与定义保持不变，v2 单独版本/ID，初始化与 Worker 默认启用 v2。现有 MatchResult 的 components_json 保存可选 evidenceStatus 与规则类型，不增加表或迁移旧记录；完整度由有状态的分项权重计算，v1 无该状态不伪造完整度。

资格从冻结职位原文以保守规则提取，优先项与必需项分开；无法可靠解释的相关条款保持待确认，不扩大 LLM 权限。画像 matchingConstraints 保存届别、身份、实习可用时间及细分方向；旧画像缺失该对象仍合法。技能可使用已有 enrichment，否则从版本化别名字典提取职位技能；未识别技能要求为未知，不能按候选人技能数作为分母。经历/项目评分取相关技能与岗位分类的最佳覆盖，不累加重复记录。

不读取当前日期推断身份或到岗能力，保证同一冻结输入可重放。明确“不限”的经历要求标为不适用；剩余权重按比例归一到 100。未知维度保留权重且记 0 已证实分；完整度小于 100 或资格 unknown 显示暂定，排序继续使用已证实总分，不把低证据结果归一成高分。

离线脱敏样本覆盖三类边界、缺失、优先项、重复经历和别名，输出新旧分数及错误排除率；无人工相关性标注时不宣称 Top-K 质量提升。

建议 Agent v3 使用用户可读的无引用结构，持久化 MatchAdvice 不保留引用目录或 kind/value 明细。Runner 在结构与内部标识校验通过后提交成功；缓存命中同样校验。手动评分失败携带已完成评分的部分结果，队列保存至 result_json，处理器定义重试 payload 以仅恢复建议阶段；不引入新的任务状态。

实现遵循 [Agent 与匹配设计](../../docs/arch/agent-and-matching.md)。

## 模块

- `packages/matching/rules`：资格规则与证据。
- `packages/matching/scoring`：维度评分、权重和总分。
- `packages/matching/rulesets`：规则集 Schema 与 v1/v2 定义。
- `packages/matching/query`：当前结果选择和稳定排序 DTO。
- `packages/matching/prompts`：job-understanding、job-advice。
- `packages/application/matching`：单个/批量计算、重算和建议任务。

## 计算流程

Worker 的 match Handler 读取不可变输入，在事务外执行：

1. 选择匹配 JobRevision 的成功 enrichment；没有则使用标准化字段并标记语义未知。
2. 运行所有 eligibility rules。
3. 按规则版本运行 v1 五维或 v2 分型 scorer，生成 components 和 total。
4. LLM 模式下把理解 Agent 输出的 fitScore 按 30/70 加权合成总分并追加 model 分项；模型分缺失时降级为规则分。
5. 以 ProfileVersion、JobRevision、实际 JobEnrichmentIdOrNone、Ruleset 和 scoringVersion 计算 inputHash，在短事务中幂等写入不可变 MatchResult。
6. eligible/uncertain 且达到建议阈值时入队 advice task；阈值默认 60，可配置，不影响分数。

JobAdviceAgent 输入只包含有效画像必要字段、职位要求、分项与证据；输出通过 Schema 后新增 MatchAdvice 并引用 AgentRun。建议失败只保留 AgentRun，不修改 MatchResult。

Web 和 CLI 统一提交 `match.score-job` 用户意图任务。规则模式直接以标准化职位字段计算；LLM 模式在同一可重试任务内顺序调用 JobUnderstanding（含模型分）、加权确定性匹配，求职建议开关启用时再调用 JobAdvice。自动评分开关开启即运行两阶段评分；建议开关只控制任务内的建议阶段，两者互不耦合。批量操作只是在应用边界为用户明确勾选的职位逐条入队，不引入全量扫描或后台自动触发。

## 当前结果

“当前匹配”由当前 ProfileVersion、Job 最新 Revision、活动 JobUnderstanding 配置对应的成功 enrichment（没有则 none）和 active Ruleset 共同确定，不使用可变 `is_current` 标记写入 MatchResult。查询优先 enrichment-aware 结果，不存在时回退基础结果；当前建议同样按活动 JobAdvice 配置选择成功 MatchAdvice。旧结果和旧建议按版本显式查询。

## 评测

- 单元：规则边界、未知证据、权重、稳定排序。
- 集成：批量分页、幂等、版本变化、取消和 Agent 失败。
- 离线：脱敏职位/画像黄金集评估 Top-K 相关性、硬排除误杀率、解释事实一致性。

首期发布门槛：黄金集硬排除误杀为 0；Top-10 人工相关率设基线并记录，不在无历史数据时虚设高阈值；建议事实一致性 100%。
