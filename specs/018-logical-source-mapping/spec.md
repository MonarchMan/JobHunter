# 018 逻辑渠道与物理来源映射规格

> 状态：Implemented
> 依赖：004, 005, 006, 017

## 目标

将用户理解的“某公司实习、校招、社招渠道”与实际执行采集的官网入口或协议拆开建模，使一个逻辑渠道能够映射零个、一个或多个物理来源，同时保持来源级审计、失败隔离和历史数据身份稳定。

## 术语

- **逻辑渠道（SourceChannel）**：公司下稳定、面向用户的 `intern | campus | social` 分类，是筛选、展示、渠道级启停和批量同步入口。
- **物理来源（JobSource）**：一个可独立配置、执行、限流、重试和观测的官方入口或协议，属于且只属于一个逻辑渠道。
- **覆盖角色（coverage role）**：物理来源在逻辑渠道中的 `required | supplemental` 角色。required 来源决定渠道是否完整支持；supplemental 来源失败不得把完整主渠道降级。

## 需求

- **LSM-001**：每家公司必须且只能拥有 `intern`、`campus`、`social` 三个逻辑渠道；逻辑渠道以 `(company_id, channel)` 唯一，并拥有稳定 UUID 和 slug。
- **LSM-002**：一个逻辑渠道可映射 `0..N` 个物理来源；每个物理来源必须且只能属于一个逻辑渠道。物理来源数量不得再由三渠道矩阵推导。
- **LSM-003**：物理来源拥有 adapter key、官方入口、非敏感配置、同步策略、游标、支持状态、运行健康、同步运行、原始记录和职位来源身份；逻辑渠道不得复制这些可变运行事实。
- **LSM-004**：逻辑渠道拥有面向用户的渠道身份和总开关。物理来源另有独立开关；只有公司、逻辑渠道和物理来源三层均启用时，物理来源才参与默认同步。
- **LSM-005**：逻辑渠道同步必须扇出为每个有效物理来源的独立 `source.sync` 任务。每个任务使用物理 `source_id` 作为幂等、并发、重试和健康边界；一个物理来源失败不得阻塞或回滚兄弟来源。
- **LSM-006**：职位身份继续使用 `(physical_source_id, external_job_id)`。R1 不因物理来源同属一个逻辑渠道而跨来源合并职位。
- **LSM-007**：缺失计数、stale/closed 判定和完整覆盖证据只能在单个物理来源的完整同步内计算，不得用一个兄弟来源的结果关闭另一个来源的职位。
- **LSM-008**：逻辑渠道支持状态由成员确定：存在至少一个 required 物理来源且所有 required 来源均为 `supported` 时为 `supported`；没有 required 来源或 required 来源全部 `blocked` 时为 `blocked`；其余情况为 `experimental`。supplemental 来源不决定渠道晋级。
- **LSM-009**：逻辑渠道运行健康只作为成员健康的派生视图，不持久化为独立事实；物理来源继续分别记录 `unknown | healthy | degraded | unhealthy`。
- **LSM-010**：物理 source slug 和 adapter key 必须全局唯一，但不再要求直接等于逻辑渠道名或固定以渠道后缀结尾；同一逻辑渠道下的多个物理来源必须使用能区分官网、业务线或协议的稳定标识。
- **LSM-011**：迁移必须保留现有 `job_sources.id` 及其关联职位、运行、任务和健康历史；新增逻辑渠道后回填 `channel_id`，旧的按物理 `source_id` 同步入口在兼容期继续可用。
- **LSM-012**：blocked 渠道不再需要为了凑齐矩阵创建虚假物理来源。只有存在真实官方入口或待验证协议时才建立物理来源；零成员渠道通过逻辑渠道说明记录阻断事实。
- **LSM-013**：Web 和 CLI 默认按逻辑渠道展示与触发同步，并允许展开查看物理来源、各自支持状态、健康和最近运行；来源级诊断仍使用物理 `source_id`。
- **LSM-014**：系统同时只能选择一个参与同步的招聘渠道类型 `intern | campus | social`，默认 `intern`。批量、单渠道、单物理来源和定时同步都必须服从该选择；切换后不得继续执行旧渠道的待处理同步任务。
- **LSM-015**：首次初始化后新增的公司、逻辑渠道和物理来源必须通过幂等 catalog 对账导入现有数据库，同时保留用户对既有来源的配置和运行历史。新导入渠道必须服从当前单渠道选择。

## 验收场景

1. catalog 中仍有每家公司三个逻辑渠道，但物理来源总数可以大于、等于或小于逻辑渠道数。（LSM-001, LSM-002, LSM-012）
2. 网易校招被建模为一个 `campus` 逻辑渠道，下面可挂互联网、游戏、雷火等多个物理官网来源；各来源拥有独立 adapter key、开关、健康与 SyncRun。（LSM-002, LSM-003, LSM-010）
3. 手动同步网易校招时生成多个来源级任务；其中一个失败时其他任务仍可成功，失败来源之外的职位不会增加 missing 计数。（LSM-005, LSM-007）
4. 两个物理来源返回相同外部职位 ID 时仍生成两个来源可追溯的职位，不发生渠道级静默合并。（LSM-006）
5. 从现有数据库迁移后，原物理来源 UUID、职位数量、同步历史和任务引用保持不变；每条物理来源都有合法 `channel_id`。（LSM-011）
6. 一个没有可验证官网入口的逻辑渠道可以没有物理来源，并派生为 `blocked`，catalog 不再注册占位 adapter。（LSM-008, LSM-012）
7. 未配置系统设置时仅实习渠道有效；选择校招后，实习与社招的手动同步、来源级同步、待处理任务和定时计划均不再执行。（LSM-014）
8. 已初始化的十家公司数据库在启动新版 Web 后自动补齐 catalog 中其余公司及渠道，既有 source UUID、开关和运行历史保持不变。（LSM-015）

## 范围外

- 跨物理来源的职位实体合并或重复职位提示。
- 将多个官网协议塞入单个复合 adapter 以模拟一对一关系。
- 跨来源共享游标、事务、限流状态或运行健康。
- 改变 `JobSourceAdapter` 的单物理来源执行边界。

## 未解决问题

无。跨来源职位去重如有需要，应作为独立规格设计，不纳入本次映射变更。
