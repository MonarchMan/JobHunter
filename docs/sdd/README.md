# JobHunter SDD 开发指南

> 状态：Accepted
> 版本：1.0.0
> 日期：2026-08-19

## 1. 适用范围

本指南规定从需求到实现的文档、评审、追踪和验收方式。总体架构与 ADR 决定系统边界；每个功能目录中的 `spec.md` 描述“必须表现出的行为”，`design.md` 描述“如何实现”，`tasks.md` 描述“按什么顺序交付和验证”。

规范中的“必须”“不得”“应该”“可以”分别表示强制要求、强制禁止、推荐要求和可选行为。

## 2. 文档状态

| 状态          | 含义                                         |
| ------------- | -------------------------------------------- |
| `Draft`       | 范围或关键决策未收敛，不得开始正式实现       |
| `Ready`       | 需求、设计、依赖、验收和任务均完整，可以实现 |
| `In Progress` | 正在实现；新发现的设计变化同步回写           |
| `Implemented` | 验收测试通过，文档与代码一致                 |
| `Superseded`  | 已被新规格或 ADR 替代，并标出替代关系        |

文档状态写在文件顶部。一个规格目录只有在三份文档均达到 `Ready` 后才能进入正式开发。

## 3. 编写规则

### 3.1 `spec.md`

必须包含：

- 目标和非目标。
- 术语、角色和前置条件。
- 带稳定 ID 的功能需求和质量需求。
- 失败、取消、重试和空数据行为。
- 可验证的验收场景。
- 与其他规格的依赖。

需求 ID 使用 `{SPEC}-{NNN}`，例如 `SYNC-004`。需求必须描述可观察行为，避免写具体类名或 SQL。

### 3.2 `design.md`

必须包含：

- 模块与数据所有权。
- 输入输出、端口和事务边界。
- 状态机或主要流程。
- 错误、安全、隐私和可观测性设计。
- 测试设计及需求到测试层级的映射。
- 被否决的主要方案或对 ADR 的引用。

设计不得重复总体架构全文，只写本能力在既定架构中的具体实现。

### 3.3 `tasks.md`

任务必须：

- 使用稳定 ID `{SPEC}-T{NNN}`。
- 能在一个小型变更中实现和验证。
- 指明前置任务、产物和验证命令/测试类型。
- 包含实现、测试、文档、迁移或固定样本工作。
- 不用“完成模块”等无法验收的笼统描述。

任务状态使用 Markdown checkbox；规格进入开发前保持未勾选，实现合并并通过验证后才能勾选。

## 4. 追踪关系

每个需求至少关联一个验收场景，每个验收场景至少落实到一个任务中的自动化测试或明确的人工验证。实现提交和测试名称应引用需求 ID。

追踪链：

```text
产品目标
  → spec 需求 ID
  → design 组件/流程
  → tasks 任务 ID
  → 测试名称与实现提交
```

无法自动化的在线官网验证必须记录日期、URL、操作和结果；它不能替代适配器固定样本测试。

## 5. Definition of Ready

规格进入正式开发前必须逐项满足：

- [ ] 目标、非目标和用户可见结果明确。
- [ ] 功能需求与质量需求都有稳定 ID。
- [ ] 正常、空数据、失败、重试、取消和重复执行行为已定义。
- [ ] 数据模型、状态转换、唯一性和事务边界已定义。
- [ ] 外部依赖及失败降级策略已定义。
- [ ] 安全、隐私、日志脱敏和数据保留要求已定义。
- [ ] 验收场景可测试且无模糊词。
- [ ] 任务覆盖所有需求和设计产物，并有依赖顺序。
- [ ] 与总体架构、ADR 和其他规格没有冲突。
- [ ] 未决问题为空；否则保持 `Draft`。

## 6. Definition of Done

功能完成必须满足：

- [ ] 所有必需任务完成并引用对应需求。
- [ ] 格式、类型、单元、集成和相关端到端测试通过。
- [ ] 迁移可从上一正式版本升级并通过完整性检查。
- [ ] 日志和错误消息完成敏感数据检查。
- [ ] 固定样本不含个人敏感信息且记录来源日期。
- [ ] 操作文档、默认配置和 `--help` 与实现一致。
- [ ] 规格状态更新为 `Implemented`。
- [ ] 若设计发生变化，架构和 ADR 已同步。

## 7. 变更控制

- 只改变局部实现且不影响外部行为：更新 `design/tasks`。
- 改变可观察行为或验收：先更新 `spec`，再实现。
- 改变依赖方向、数据所有权、持久化核心、进程职责或安全边界：先提交 ADR 和总体架构修改。
- 官网页面或接口变化：更新来源调研和适配器固定样本，不应直接修改公共领域模型来迎合单一来源。
- Prompt 或模型配置变化：提升版本并运行黄金集，不覆盖旧运行记录。

## 8. 验证层级

| 层级        | 用途                                             |
| ----------- | ------------------------------------------------ |
| Schema/单元 | 值对象、状态机、规则、序列化、缓存键             |
| 契约        | Repository、来源适配器、模型客户端、任务 Handler |
| 集成        | SQLite 迁移与事务、Worker 恢复、文件存储         |
| 端到端      | CLI/后续 Web 到本地数据库的完整闭环              |
| 在线 Smoke  | 官网入口和最小发现能力，仅手动或受控计划执行     |
| 离线评测    | Agent 黄金集和匹配排序质量                       |

在线 Smoke 失败不能通过放宽离线契约来隐藏；应明确判断是来源变化、网络限制还是实现缺陷。
