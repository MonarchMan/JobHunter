# ADR-0055：招聘邮件采用独立事件域、本地增量轮询与最小持久化

- 状态：Accepted
- 日期：2026-10-14

## 背景

JobHunter 已经能够同步职位、建立个人资料并进行匹配，但用户投递后的笔试、面试、流程结束和 Offer 通知仍散落在邮箱中。该信息与职位来源有三项根本差异：

1. 邮箱是用户授权的私有数据源，不是公开职位来源，凭据、正文和个人标识具有更高隐私要求。
2. 邮件表达申请流程事件，不具备官网同步的完整覆盖、连续缺失和职位关闭语义；同一邮件岗位也可能不在正式职位库中。
3. Gmail、Microsoft Graph 和 IMAP 的授权、稳定消息身份、文件夹及增量游标不同，但分类、申请状态和隐私规则必须保持一致。

本地部署默认没有稳定公网回调地址。若首版直接建设提供商推送，需要额外的云消息、Webhook、订阅续期和外网安全边界；若把全部邮件直接交给模型，则会扩大隐私、成本、提示注入和误判风险。

## 决策

1. 建立独立的招聘邮件与求职申请领域，不把邮箱建模为 `JobSource`，不复用职位缺失下架状态机。邮件可以创建或更新 `JobApplication` 和 `ApplicationEvent`，但不得修改 `Job` 的内容或生命周期。
2. 邮箱能力按目录聚合为两个嵌套 workspace 包：`packages/mail/core` 保存提供商无关协议、DTO、错误和契约测试；`packages/mail/connectors` 保存 OAuth、IMAP、提供商 SDK 和凭据库等基础设施实现。应用层只依赖 `mail/core`，具体连接器只由 `apps/*` 装配。
3. 首版采用 Worker 驱动的本地增量轮询。邮箱账号、provider、文件夹、计划、脱敏地址和 `credentialRef` 保存在本地非敏感配置；增量游标、连接代次和最近运行状态保存在数据目录运行状态文件，并以临时文件加原子替换更新。连接器优先使用提供商游标；不支持全局稳定 ID 的协议生成包含文件夹代次的稳定消息键。游标失效时执行有界重建，不建设公网 Webhook 或推送代理。
4. 首版连接器范围固定为 `gmail`、`microsoft-graph` 和 `imap`。Gmail 使用 OAuth `gmail.readonly`、有界 `messages.list` 与 `historyId`；Microsoft Graph 使用 delegated `Mail.Read`、文件夹级 delta、ImmutableId 和安全 `webLink`；IMAP 强制 TLS 和只读会话，以文件夹身份、`UIDVALIDITY + UID` 建立稳定消息键，并在服务端支持时使用 CONDSTORE/QRESYNC。三者独立经过授权、首次回溯、增量、游标恢复、断开和重新授权门禁；全部 supported 后才算 M1 完整交付。
5. 邮件处理拆成轻量发现和按需正文两个阶段。同步任务先保存最小消息引用并发布分类任务；分类任务才在事务外读取有界主题、发件信息和正文并清洗 HTML。日历和其他附件均不读取、不解析、不发送给模型，远程资源和链接目标也不由系统获取。
6. 分类采用“确定性规则高召回候选筛选、无工具 Agent 最终语义分类与字段提取、低置信人工复核”。稳定的营销、宣讲、问卷、验证码等负例可直接排除，未知但具有招聘流程信号的模板必须保守放行。配置模型默认关闭；启用时只发送当前候选所需的清洗文本。邮件正文视为不可信输入，Agent 不拥有工具，输出必须通过 Schema 与业务规则双重校验。首版人工操作只允许确认、忽略以及选择或创建申请关联，不提供字段和既有事件更正。
7. 不归档完整邮箱。与招聘无关和待确认的邮件只保存去重所需身份、内容哈希与处理结论；用户打开待确认详情时按消息引用重新读取并分类，不持久化中间分类结果。已确认事实进入申请事件。不保存原始 MIME、完整 HTML、普通附件或模型输入正文。
8. Token、刷新令牌和应用专用密码进入操作系统或等价安全凭据库。本地非敏感配置只保存不可直接使用的 `credentialRef` 与脱敏账号信息；SQLite、运行状态、任务、日志、备份和诊断不得包含秘密或邮件正文。为支持设置页维护 IMAP 连接，已保存的 IMAP 授权码仅在用户主动点击显示按钮时经无缓存受控接口临时回传，默认隐藏且隐藏后清理前端明文；Gmail 和 Microsoft OAuth 令牌仍永不回传。
9. SQLite 只新增 `mail_message_refs`、`job_applications` 和 `application_events` 三张表，不建立邮箱连接、游标或招聘分类版本表。`mail_message_refs` 使用稳定邮箱键、外部消息键和内容版本支撑重放与重取，并保存可选的清洗后来源 URL；`application_events` 直接保存分类器版本、置信度、结构化事件和邮件引用。申请当前态在同一短事务更新，完整时间线由专用 `application_events` 保存，而不是退化为无外键的通用事件 JSON。

## 备选方案

### 复用职位来源与同步运行

拒绝。职位来源的 coverage、missing count 和 closed 规则不适用于私人邮件；混用会使拒信或 Offer 反向污染职位事实，也会把邮箱凭据带入来源模块。

### 只实现一个巨大邮箱模块

拒绝。协议契约与提供商 SDK 混在同一目录会使应用层难以只依赖抽象，也不利于公共契约测试。采用 `mail/core` 与 `mail/connectors` 保留边界，同时用 `packages/mail` 聚合相关目录，避免继续平铺顶层包。

### 首版使用 Webhook 或提供商推送

拒绝。该方案要求公网入口、订阅续期和额外云基础设施，与当前个人本地部署及模块化单体目标不匹配。轮询已经可以利用提供商增量游标，后续只有在明确的延迟需求和部署条件下才通过新 ADR 引入推送。

### 全部邮件直接交给 LLM

拒绝。它会发送大量无关私人邮件，成本和误判不可控，也难以通过固定规则解释。确定性粗筛和模板识别必须先执行，模型只处理有限候选；规则不独自生成最终招聘事件，以免模板歧义造成错误结构化事实。

### 保存完整原始邮件以便重放

拒绝。原始邮箱归档超出产品目标，并显著扩大备份、删除、泄露和附件安全风险。分类升级需要重跑时优先按消息引用重新读取；原邮件已删除时保留既有结构化事件，不承诺重新分类。

## 结果

- 新增 `MailboxConfig`、`MailboxRuntimeState`、`MailMessageRef`、`JobApplication` 和 `ApplicationEvent` 等概念；SQLite 只新增三张专用表。
- 首版必须同时维护 Gmail、Microsoft Graph 和通用 IMAP 三套协议实现及隔离账号 smoke；任一连接器未通过门禁时只能单独标记 experimental 或 blocked，不能把整体 M1 标记为完整交付。
- Worker 新增邮箱同步、邮件分类和保留任务，并复用现有租约、并发键、共享网络信号量和错误分类机制。
- Web 新增邮箱设置、待确认和申请时间线；邮箱读取仍只在 Worker 中执行。
- `pnpm-workspace.yaml`、TypeScript references、dependency-cruiser 和构建脚本需要认识 `packages/mail/*` 的嵌套 workspace 布局。
- 备份只包含非秘密的邮箱配置、运行状态与招聘进展数据；恢复后若凭据引用不可用，必须重新授权邮箱才能继续读取。
- 若未来需要保存完整招聘邮件、解析任何附件、自动操作邮箱或使用公网推送，必须新增规格和 ADR，重新评估加密、恶意内容、保留和权限边界。
