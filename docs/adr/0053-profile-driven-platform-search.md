# ADR-0053：招聘平台按资料意向岗位逐词搜索

状态：已接受（2026-09-30）

## 背景

四个平台的官网都提供关键词搜索，但当前生产连接器混用了推荐流、已打开的搜索页和智联显式关键词。个人资料的 `targetRoles` 承担既有职位类别选择、官网同步与匹配职责。直接把“研发”等大类作为平台搜索词会带来大量无关职位，替换该字段又会破坏原类别选择；因此需要独立的具体意向字段。继续把推荐流标为搜索不能保证结果对应用户意向。

## 决策

1. 保留 `targetRoles` 的职位类别职责和原有下拉框，继续供官网同步门禁与匹配使用；新增独立可选数组 `intendedRoles` 保存用户填写的具体意向职位。平台搜索仅使用后者，不拼接或回退到 `targetRoles`、`targetSubfamily`。旧资料不自动把大类复制到新字段，未填写时按缺词处理；人工意向在简历重新提取时保留，与用户偏好一致。
2. 日常获取使用按创建时间排序的第一份资料的当前版本。连接时在应用层冻结资料版本和规范化关键词，单次上限 10 个词，防止一个动作意外放大为大量浏览器连接与请求；缺资料、无意向词或在新字段填写一级大类应明确拒绝并引导用户填写具体职位，不要求改写原职位类别，不退回推荐流，也不使用代码里的示例关键词。
3. 每个平台的一次“获取职位”对每个不同关键词分别读取当前一批，按该平台稳定职位 ID 合并去重，然后补齐有效详情并写入同一个平台来源。重复职位只请求、保存一次详情；跨词重复不视为上游分页重复。下一次显式获取沿用每个关键词各自的下一批游标；改变意向词须显式重连。
4. 应用层负责资料选择、关键词计划、批次合并和正式入库；平台连接器负责按真实官网搜索协议建立每词会话。BOSS 保持浏览器辅助 JSON 观察，智联与猎聘优先独立 HTTP，前程无忧继续让官网自然生成签名模板后由独立 HTTP 获取。不得把推荐、DOM 摘要、旧签名或旧关键词响应作为搜索成功。
5. 一个提供方仍只有一个逻辑连接和来源身份；词级会话是该逻辑连接的私有组成，不新增职位来源、账号池或独立存储生命周期。任一关键词失败时整次任务明确失败并保留已提交职位，不把部分成功标为完整成功。

## 后果

资料编辑器、Worker 装配和四个连接器需要同时演进；既有推荐能力可保留为显式诊断入口，但日常“获取职位”不能隐式使用它。上线前须逐平台验证关键词、至少一批列表、有效详情、跨词去重和职位页查询；无法通过的平台应显示未支持的搜索能力，而非默默采集推荐职位。
