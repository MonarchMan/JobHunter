# 关键改进记录

本文件仅记录项目通过引入、替换或改进组件而获得的持续性提升，按日期倒序分章，同一天的改进使用有序列表记录，不替代功能规格、架构决策或 Git 提交日志。组件包括基础设施、数据访问模块、任务调度机制和共享 UI 等项目组成部分。

## 记录规则

1. 每条记录以“问题 + 措施 + 指标”为核心，明确涉及的组件、改动机制与对应收益，补充验证条件、限制和关联资料。常规 bug 修复、一次性数据库整理、备份、重启、手动重跑和临时数据修复不纳入本文件；若后续实现可持续运行的维护组件，则记录该组件及其收益。
2. 优化前先记录基线，实施后补充实测结果；未测量的收益标为“待验证”，不得倒推或补造基线。
3. 优化前后应保持测量范围、环境、数据规模和请求条件一致，并说明样本数量。条件不完全一致时应注明，避免将观察结果当作严格基准。
4. 数据库查询耗时、HTTP 响应耗时与浏览器可交互时间分别记录。首次加载与热请求分别统计，不混算提升比例。
5. 耗时减少比例按“（优化前耗时 − 优化后耗时）/ 优化前耗时”计算；基线只有范围时使用近似区间，并说明比较依据。
6. 同一天只保留一个日期章节，章内各项改进按完成顺序使用 1、2、3……有序列表；同日新增改进追加到该章末尾，延续编号，新日期章节放在已有日期章节之前。后续关键改进完成验证后按下方模板追加；仍待验证的条目在取得结果后更新，保留验证日期与重要条件变化。

## 2026-09-05

1. **任务页批次聚合与详情查询优化**

   **问题**

   任务页热请求耗时较高，即使完成开发模式首次路由编译，再次访问仍需约 1.47～1.61 秒。

   诊断查询存在以下开销：

   - 总数统计与分页列表分别执行完整批次聚合。
   - 查询时解析任务 JSON 中的运行和来源字段，并递归计算重试根。
   - 窗口排序携带完整任务行，增加不必要的数据处理。
   - 普通任务先返回 ID，再逐条读取任务；来源同步任务还需逐条查询关联运行信息。

   **措施**

   1. 将总数统计与分页合并为一次 SQL，共用物化聚合结果；空页仍返回总数，保留越界页回落行为。
   2. 收窄窗口排序的输入字段，仅保留批次统计需要的 ID、状态、时间与批次键。
   3. 在任务表持久化 `source_run_id`、`source_id` 和 `retry_root_task_id`，回填历史数据并建立组合索引。插入触发器统一维护投影，查询不再实时解析详情 payload 或递归计算重试链。
   4. 当前页普通任务及关联来源运行信息改为一次批量读取，仅返回脱敏展示字段，消除逐条查询。

   **指标**

   | 测量范围                                            | 优化前               | 优化后                      | 提升                                      |
   | --------------------------------------------------- | -------------------- | --------------------------- | ----------------------------------------- |
   | 第一阶段：任务页 HTTP 热请求                        | 1.47～1.61s          | 0.86～0.97s                 | 耗时约减少 35%～45%，为观测区间的粗略比较 |
   | 第二阶段：任务页 HTTP 热请求                        | 0.86～0.97s          | 平均 304ms，范围 268～368ms | 新均值相对旧区间耗时约减少 65%～69%       |
   | 第二阶段：数据库副本上的批次聚合查询                | 未记录同口径独立基线 | 10～14ms                    | 不计算提升比例                            |
   | 第二阶段：数据库副本上的普通任务详情批量读取，23 条 | 未记录同口径独立基线 | 热查询 1～2ms，首次约 12ms  | 不计算提升比例                            |

2. **SQLite 自动阈值维护组件**

   **问题**

   SQLite 删除记录后通常复用空闲页而不缩小主文件。此前项目没有周期性空间检查、阈值整理和跨进程写保护，需人工判断整理时机；直接在 Worker 主线程执行 VACUUM 也会阻塞事件循环。

   **措施**

   引入应用层维护服务和数据库维护仓储，由 Worker 驱动独立子进程：每 30 分钟检查 WAL，每天检查空闲页并 optimize；批量清理至少 1,000 条记录后请求补查。WAL 达到 64 MiB 先 PASSIVE，空闲时仍超阈值才 TRUNCATE；主库空闲比例至少 25%、空闲空间至少 64 MiB 且满足 7 天成功整理冷却期，才执行 VACUUM。

   整理前原子检查任务与近期调度，并通过跨连接写保护暂停业务写入；读请求继续，写入受阻时返回可重试 503。检查磁盘余量后创建一致性备份，校验备份和整理后数据库；只轮换组件目录中的已验证自动备份，保留最近两份。日常无操作检查只更新摘要，实际维护留下单条只读审计任务。

   **指标**

   | 测量范围                     | 原状态               | 组件执行结果                                 |
   | ---------------------------- | -------------------- | -------------------------------------------- |
   | 合成样本主文件大小           | 2,351,104 字节       | 606,208 字节，减少约 74.2%                   |
   | 合成样本空闲页空间           | 1,732,608 字节       | 0 字节                                       |
   | 保留样本与完整性             | 1 条、8,192 字节正文 | 仍为 1 条、8,192 字节；integrity_check 为 ok |
   | 连续三次成功维护后的自动备份 | 无自动轮换           | 仅保留 2 份已验证备份；手工文件不变          |
   | 无操作周期的任务增量         | 无周期检查           | 0 条任务，仅更新单例摘要                     |

   **验证条件**

   2026-09-05，本机 Node.js 24、SQLite；在独立临时数据库创建 200 条每条 8 KiB 的样本，删除其中 199 条并 checkpoint，再调用实际维护仓储。单次完整维护约 49.1ms；该小样本耗时不代表真实业务库耗时。测试直接调用维护动作绕过生产 64 MiB 阈值，阈值及冷却期另由应用层测试覆盖。

   全量单元测试 317 项通过；维护、迁移、任务 Worker、清理集成测试 38 项通过；HTTP 503、只读审计及诊断测试 5 项通过。浏览器覆盖任务页 1280/768px 无障碍检查，以及 1280/390px 维护记录无重试/取消入口、键盘打开详情和关闭后焦点恢复。生产 Web 构建通过。

   **边界与关联**

   这是持续运行组件的合成样本验证，不是此前人工空间整理的收益记录；真实业务长期空间增长与检查开销仍待试运行观察。auto_vacuum 保持 NONE，不更改业务删除策略。检查摘要保存于 database_maintenance，实际维护记录类型为 maintenance.sqlite，Worker 输出 database.maintenance 事件。升级时需先停止旧 Web 和 Worker，再启动新版本，保证全部连接安装写保护。

   - [运维规格](../../specs/012-operations/spec.md)：OPS-012～OPS-015。
   - [ADR-0020：SQLite 阈值维护与跨进程写入保护](../adr/0020-sqlite-automatic-maintenance.md)。
   - [维护应用服务](../../packages/application/src/operations/sqlite-maintenance-service.ts)。

3. **首页精选查询与运行时异常恢复**

   **问题**

   首页只返回五条精选职位，却对全部历史修订做窗口排名并关联一次未使用的修订表。运行时还存在三个恢复缺口：普通数据库锁冲突会退出 Worker 领取循环；Web 容器永久缓存失败 Promise；维护子进程与普通调度串行等待，退出取消要等 engine.run 返回后才执行。

   **措施**

   - 首页精选通过已有 (job_id, revision_no) 唯一索引定位最新修订，移除全量排名和冗余关联，保持筛选、排序与字段不变。
   - Worker 初始化后同步锁等待降为 100ms，锁忙识别由数据库基础设施通过装配回调提供。领取和调度采用异步退避；心跳锁忙不伪报续租成功；结果提交遇锁保留持久化租约恢复，不写成业务永久失败。非锁错误仍会正常暴露。
   - Web 并发请求复用同一次初始化，失败只缓存 1 秒，随后由下一请求重试；成功容器持续复用。
   - 周期维护使用独立异步循环，直接接收引擎生命周期取消信号，并等待子进程 close 后收敛；提前退出时清理宽限定时器。

   **指标**

   | 范围                                | 改进前                                      | 改进后                                               |
   | ----------------------------------- | ------------------------------------------- | ---------------------------------------------------- |
   | 首页精选 SQL，5 次热查询            | 499.08～658.87ms，均值 549.96ms             | 34.00～40.27ms，均值 37.09ms，平均耗时减少约 93.3%   |
   | 完整首页数据库 snapshot，5 次热调用 | 本轮未测量同口径旧值                        | 37.53～57.57ms，均值 43.55ms；不是 HTTP 或浏览器耗时 |
   | Worker 运行期同步锁等待配置         | 5,000ms                                     | 100ms，后续异步退避；不是所有 SQL 的耗时上限         |
   | Web 初始化失败后的恢复              | 失败 Promise 一直复用                       | 1 秒退避后可重新尝试，测试验证并发合并及成功复用     |
   | 维护期间退出                        | 等维护完成或最长 5 分钟超时后才能触发 close | 引擎停止时直接取消子进程；实际子进程取消测试通过     |

   **验证条件**

   2026-09-05，本机 Node.js 24、SQLite，16,180 条职位和 18,358 条修订。只读连接在同一读事务内比较 Git HEAD 中旧精选 SQL 与新仓储 SQL，返回行完全一致。每组执行六次，第一次数值单列为旧查询 549.98ms、新查询 34.93ms、完整新 snapshot 49.49ms，其余五次作为热样本。未修改真实库或触发官网/模型请求；该小样本不是压力测试。

   测试覆盖真实双连接争锁后的任务完成、调度锁忙恢复、心跳锁忙恢复、提交锁忙后的租约保留、非锁错误传播、维护与调度独立、退出取消实际子进程，以及 Web 初始化失败恢复。首页覆盖多修订、旧高分/新低分、新修订排除与关闭职位。

   验证结果：318 项全量单元测试、26 项相关集成测试、6 项初始化/诊断接口测试通过；生产 Web 构建、类型、ESLint、格式、文档和依赖边界检查通过。

   **边界与关联**

   本轮不修改评分列表语义、关键词检索、完整性检查策略、业务数据保留策略或官网速率。运行期锁忙后的提交恢复仍遵循既有至少一次执行和幂等约束。需要重启 Web/Worker 才能加载新的运行时逻辑。

   - [首页查询](../../packages/db/src/dashboard-read-model.ts)、[Worker 引擎](../../packages/application/src/tasks/worker-engine.ts)。

4. **连接校验分层与关键词分页复用**

   **问题**

   首次 Web 容器初始化会随数据库连接执行完整性和外键全库检查；页码关键词查询分别计数、取页，重复扫描正文。

   **措施**

   - 普通数据库连接只做能力、配置和迁移变化判断；新库、实际迁移及显式验证保留完整检查。恢复验证显式开启检查，doctor 和维护检查保持不变。
   - 关键词页码查询通过 MATERIALIZED CTE 复用一次匹配结果，物化字段不包含正文；计数和取页共享结果，并保留空页、越界回落、排序、转义及游标语义。
   - 复核上一批维护退出修复：退出取消实际子进程，并等待 close 后释放连接；本批未重复修改该组件。

   **指标**

   | 测量范围                        | 优化前  | 优化后  | 改善             |
   | ------------------------------- | ------- | ------- | ---------------- |
   | Java 关键词页码查询，热查询均值 | 85.58ms | 50.58ms | 耗时减少约 40.9% |
   | 页码关键词 SQL / 正文匹配次数   | 2 / 2   | 1 / 1   | 不再重复扫描正文 |
   | 普通重连的完整性扫描调用次数    | 1       | 0       | 移出普通连接路径 |

   **验证条件**

   2026-09-05，本机 Node 24 / better-sqlite3，在实际数据库同一只读事务中交替执行旧计数加分页 SQL、新仓储查询各 7 次，排除首轮后取 6 次均值。关键词 Java 命中 5,033 条，第 1 页每页 20 条，逐轮验证总数及职位 ID 顺序一致。旧值不含领域映射，新值包含仓储映射。独立测得完整性加外键检查 1,063.65ms，元数据探针 0.08ms；这两项不是完整连接或 HTTP 耗时，不计算整页提升比例。

   58 项相关集成测试及 2 项维护子进程测试通过，覆盖新库、升级、普通重连、显式检查、恢复、分页边界及退出回归。

   **边界与关联**

   仍使用 LIKE 子串匹配，首次匹配依然需要扫描候选正文，不是索引搜索；不调整开发模式首次路由编译。普通连接不再保证检测所有历史数据损坏，深度诊断应使用 doctor。新建库与迁移仍支付完整检查成本。对应 [持久化规格](../../specs/002-sqlite-persistence/spec.md) 和 [存储收敛决策](../adr/0012-final-storage-convergence.md)。
